# MailShield(메일쉴드) 개발 계획서

## 1. 문서 개요

### 1.1. 목적

본 문서는 `00.먼저 앱정의서.md`와 `01.기능명세서.md`를 기준으로 MailShield의 제품 형태, 시스템 구조, 기술 스택, 개발 순서, 검증 기준 및 배포 계획을 정의한다.

### 1.2. 최종 제품 형태 확정

MailShield의 최종 제품은 **Windows 메모리 상주형 이메일 보안 에이전트와 관리자 웹 콘솔로 구성된 하이브리드 서비스**로 확정한다.

- Windows 로그인 또는 시스템 시작 시 에이전트가 자동 실행된다.
- 에이전트는 백그라운드에서 이메일 발송 위험과 계정 상태를 지속적으로 감시한다.
- 사용자에게는 시스템 트레이 아이콘, Windows 알림 및 발송 전 경고 화면을 제공한다.
- 중앙 서버는 이메일 분석, 조직 정책, 위험 점수, 관리자 알림 및 감사 이력을 관리한다.
- 관리자는 웹 콘솔에서 위험 사용자, 위험 메일, 미처리 사건과 조직 정책을 확인한다.
- 수신 위협 진단도 제공하지만 최우선 목적은 **이메일을 통해 외부로 빠져나가는 정보 유출을 사전에 감시하고 관리자가 누가 위험한지 알 수 있게 하는 것**이다.
- 이메일 주소를 입력하면 공개 DNS와 표준 자동설정 정보로 공급자와 보안 상태를 먼저 진단하고, 사용자 인증 후 메일함 심층 분석을 수행한다.

### 1.2.1. 최종 Windows 앱 실행 형태

| 단계 | 실행 형태 | 대상 | 동작 | 상태·배포 판단 |
|---|---|---|---|---|
| 0 | `realtime_email_monitor.pyw` (CLI) | 개발자 검증 | 콘솔에서 환경변수로 실행, IMAP IDLE 감시, 로그 파일 기록 | 2026-09-07 Gmail 실탐지 검증 완료. 이후 회귀 테스트·현장 재현용으로만 유지 |
| 1 | **MailShield Tray (Python 상주형 앱)** | 개인·파일럿 사용자 | 로그인 시 자동 실행, 트레이 아이콘, Toast 알림, 계정 연결 UI, 자격증명 보안 저장, 단일 인스턴스, 단일 exe 배포 | **현재 목표.** 18장 전환 계획에 따라 구현 |
| 2 | Windows Service + WPF Tray (.NET) | 조직 운영 환경 | 자동 시작, 장애 복구, 권한 분리, 정책 동기화, 중앙 보고 | 최종 운영 방식. 1단계에서 검증한 감시 로직을 이식 |

CLI 프로토타입은 목적을 달성했으므로 개발 목표를 **Windows RAM 상주형 앱**으로 전환한다. 1단계는 검증된 Python 감시 코드를 그대로 재사용해 가장 빠르게 상주형 앱을 만들고, 2단계는 조직 배포 요건(서비스 권한 분리, 정책 동기화, 서명 설치)을 위해 .NET으로 이식한다. 상세 계획은 18장에 정의한다.

`.pyw`는 파일 확장자만으로 RAM 상주와 안정적인 서비스 운영을 보장하지 않는다. 최종 앱은 감시 엔진을 서비스로 실행하고, 사용자가 상태를 확인할 수 있는 트레이 UI와 Windows Toast 알림을 결합한다. Python 기반 IDLE 작업자를 사용할 경우 서비스가 해당 프로세스의 생존, 재시작, 로그 필터링과 업데이트를 관리한다.

### 1.3. 개발 원칙

- 이메일 원문과 개인정보의 외부 전송을 최소화한다.
- 가능한 분석은 로컬 에이전트에서 먼저 수행한다.
- 중앙 서버에는 마스킹된 탐지 근거와 사건 메타데이터를 우선 전송한다.
- 발송 차단은 명확한 정책과 연동 지점이 있는 경우에만 수행한다.
- 탐지 결과만으로 사용자를 위험 인물로 단정하지 않고 관리자 검토 절차를 제공한다.
- 모든 기능은 `FN-*`, 테스트는 `TC-*` 식별자로 추적한다.

## 2. 제품 구성

### 2.1. Windows 상주형 에이전트

Windows 에이전트는 다음 구성요소로 나눈다.

| 구성요소 | 역할 |
|---|---|
| Windows Service | 자동 시작, 백그라운드 작업, 정책 동기화, 검사 큐 및 서버 통신 |
| System Tray App | 사용자 상태 표시, 경고, 진단 결과, 일시 중지 및 계정 연결 UI |
| Discovery/Mail Connector | DNS·Autoconfig·Autodiscover 탐지, 공급자별 OAuth·표준 IMAP 및 Outlook 이벤트 수집 |
| Local Analysis Engine | 수신자, 본문, URL, MIME, 첨부파일 및 민감정보 1차 분석 |
| File Provenance Monitor | 등록 프로그램의 파일 생성 이벤트와 이메일 첨부·발송 이벤트 연계 |
| Policy Engine | 조직 정책에 따라 허용, 경고, 보류 및 차단 판단 |
| Secure Local Store | 토큰, 정책 캐시, 미전송 사건과 감사 큐의 암호화 저장 |
| Updater | 서명된 버전 확인, 안전한 자동 업데이트 및 롤백 |

서비스와 트레이 앱은 권한을 분리한다. 서비스는 백그라운드 처리만 담당하며, 사용자 UI는 제한된 사용자 권한으로 실행한다. 프로세스 간 통신은 인증된 Named Pipe를 기본으로 사용한다.

### 2.2. 중앙 백엔드

- 에이전트 등록, 장치 인증 및 정책 배포
- DNS 기반 공급자 탐지, 표준 IMAP과 공급자별 OAuth/API 연동
- AI 피싱 문맥 분석과 위험 점수 집계
- 악성 URL·파일 해시 및 계정 유출 이력 조회
- 관리자 사건, 알림, 승인 및 감사 이력 관리
- 조직·사용자·장치별 상태와 통계 제공

### 2.3. 관리자 웹 콘솔

- 조직 전체 보안 현황
- 위험도가 높은 사용자와 사건 목록
- 위험 유형, 기간, 사용자 및 처리 상태별 필터
- 사건 상세 근거와 승인·차단·오탐 처리
- 내부 도메인, 민감정보, 예외 및 발송 제어 정책 설정
- 감사 기록 조회와 권한 기반 보고서 내보내기

```text

          |
          | TLS + 장치 인증
          v
[FastAPI Backend] ---- [AI 분석 공급자]
    |     |   |        [파일/URL 평판 API]
    |     |   +--------[유출정보 API]
    |     +------------[DNS Resolver]
    v
[PostgreSQL / 작업 큐 / 암호화 저장소]
    |
    +---- [관리자 Web Console]
    +---- [이메일·문자·Slack/Teams 알림]
```

### 3.1. 발송 전 처리 흐름

1. Outlook 연동 모듈 등 지원되는 연결 지점에서 발송 시도를 감지한다.
2. 에이전트가 수신자, 본문, URL, 첨부파일과 로컬 정책을 분석한다.
3. 추가 판단이 필요하면 마스킹된 특징값 또는 정책상 허용된 데이터를 서버로 전송한다.
4. 로컬·서버 분석 결과를 합산하여 위험도를 산출한다.
5. 안전은 발송하고, 주의는 사용자에게 재확인을 요청한다.
6. 위험은 발송을 보류하고 관리자에게 알리며, 긴급은 정책에 따라 차단한다.
7. 사건 ID, 판단 근거, 사용자 행동 및 관리자 조치를 감사 이력에 저장한다.

### 3.2. 연동 방식별 통제 범위

| 연동 방식 | 감시 범위 | 발송 전 경고/차단 | 비고 |
|---|---|---|---|
| Outlook 데스크톱 연동 | Outlook에서 작성·발송하는 메일 | 지원 가능 | MVP의 발송 전 통제 우선 대상 |
| Gmail API | Gmail 계정의 메일과 변경 상태 | 기본적으로 발송 후 감시 중심 | OAuth 동의 및 API 정책 준수 필요 |
| IMAP | 메일함 조회와 MIME 분석 | 일반적으로 발송 전 차단 불가 | 진단·사후 탐지용 |
| 조직 메일 게이트웨이 | 조직을 통과하는 송수신 메일 | 가장 강력한 중앙 통제 | 추후 기업형 확장 |

공개 진단은 이메일 주소만으로 MX, SPF, DMARC, MTA-STS와 검증 가능한 TLS 상태를 평가한다. 본문과 첨부파일은 인증과 권한 동의 후 분석한다. MX는 수신 서버이므로 IMAP 서버와 동일하다고 가정하지 않고 SRV, 검증된 ISP 메타데이터, Autoconfig/Autodiscover 및 공급자 지문을 순서대로 검증한다.

> Gmail API나 IMAP 조회만으로 브라우저, 모바일, 다른 클라이언트에서 이루어지는 모든 발송을 사전에 차단할 수는 없다. 따라서 MVP의 확실한 발송 전 통제 범위는 Windows Outlook 연동으로 한정하고, Gmail/IMAP은 계정 진단과 발송 후 조기 탐지를 제공한다.

| 메일 인증 | DNS Resolver, SPF/DKIM/DMARC 라이브러리 | 발신 서버와 헤더 인증 검증 |
| 관측성 | OpenTelemetry, 구조화 로그, 오류 추적 | 에이전트·서버 상태와 장애 추적 |
| 배포 | MSIX 또는 서명된 MSI, Docker, CI/CD | Windows 설치·업데이트와 서버 배포 자동화 |

### 4.2. 기술 선정 시 확인 사항

- Gemini, VirusTotal 및 HIBP의 모델명, 요금, 호출 제한과 데이터 처리 약관은 구현 시점에 공식 문서로 재검증한다.
- 공급자별 OAuth 범위, 앱 검증과 API 정책을 확인한다.
- 자동 탐지는 후보 제시 기능이며 TLS와 인증 성공 전 서버를 확정하지 않는다.
- 일반 계정 비밀번호 수집은 기본 흐름에서 제외하고 OAuth·앱 비밀번호를 우선한다.
- Outlook 버전별 발송 이벤트와 차단 기능 차이를 기술 검증(Spike)으로 확인한다.
- 외부 서비스에 이메일 원문이나 파일을 전송할 때는 조직 정책과 사용자 동의를 적용한다.
- 악성 파일 평판 조회는 가능하면 파일 원본 업로드 대신 SHA-256 해시 조회를 우선한다.

## 6. 데이터 처리 및 보안 설계

### 6.1. 데이터 최소화

- 로컬 분석 결과는 기본적으로 유형, 점수, 마스킹된 근거와 해시 형태로 서버에 전달한다.
- 이메일 원문과 첨부파일은 기본 저장 대상에서 제외한다.
- 정밀 분석에 원문이 필요한 경우 별도 동의, 보존 기간과 접근 권한을 적용한다.
- 화면, 로그, 알림에는 주민등록번호, 계좌번호, 토큰 등 전체 값을 표시하지 않는다.
- 주민등록번호·여권번호 등 고유식별정보와 카드·계좌정보는 로컬에서 우선 탐지하고 중앙 서버에는 유형, 건수, 위험 점수와 마스킹 근거만 전송한다.

### 6.1.1. 개인정보·금융정보 탐지 엔진

- 정규식만 사용하지 않고 체크섬, 날짜·길이 유효성, 키워드와 주변 문맥을 결합한다.
- 카드번호는 Luhn 검사, BIN/IIN 후보와 결제 문맥을 사용하되 카드사 추정값을 확정 정보로 표시하지 않는다.
- 계좌번호는 공백·하이픈을 정규화하고 은행별 형식 후보와 은행명·예금주·송금 문맥을 결합한다.
- 주민등록번호 등 고유식별정보는 유효 형식과 날짜 문맥을 평가하되 탐지값을 즉시 마스킹한다.
- 이름·주소·연락처 등 단독 식별자의 확신도는 낮게 두고 여러 식별자가 결합되면 위험도를 높인다.
- PDF, Office 문서와 스프레드시트는 격리된 파서로 텍스트를 추출하고 매크로를 실행하지 않는다.
- 암호화·손상·미지원 파일은 `검사 불가` 상태로 정책 엔진에 전달한다.
- 개인정보 유형별 정밀도·재현율과 업무 문서 오탐률을 별도로 측정한다.

### 6.2. 인증정보 보호

- Google OAuth를 우선하며 사용자 비밀번호와 앱 비밀번호의 직접 수집은 기본 설계에서 제외한다.
- Access Token과 Refresh Token은 Windows DPAPI 또는 서버 비밀 저장소로 암호화한다.
- 메모리 내 평문 데이터는 사용 후 참조를 제거하고 불필요하게 복제하지 않는다.
- 로그, 크래시 덤프 및 분석 이벤트에 토큰과 이메일 원문이 포함되지 않도록 필터링한다.
- 연결 해제 또는 장치 폐기 시 토큰을 폐기하고 로컬 자격정보를 제거한다.

> 관리형 런타임에서는 문자열의 물리적 메모리 즉시 삭제를 완전히 보장하기 어렵다. 따라서 “메모리 파기” 문구에만 의존하지 않고 비밀번호 미수집, 짧은 수명, 최소 복사, 보안 저장소, 덤프 제한과 프로세스 격리를 함께 적용한다.

### 6.3. 에이전트 보안

- 설치 파일과 업데이트 패키지에 코드 서명을 적용한다.
- 서버 인증서 검증과 장치별 인증서를 사용한다.
- 서비스와 트레이 앱의 IPC 요청자를 검증한다.
- 정책 파일에 서명을 적용하고 위변조 시 마지막 정상 정책을 사용한다.
- 에이전트 제거와 보호 기능 중지는 권한 및 조직 정책에 따라 통제한다.
- 자동 업데이트 실패 시 이전 정상 버전으로 롤백한다.

### 6.4. 권한과 감사

- 사용자, 관리자, 시스템 관리자의 역할을 분리한다.
- 조직별 데이터를 논리적으로 격리한다.
- 조회, 승인, 차단, 해제, 정책 변경 및 내보내기를 감사 로그로 남긴다.
- 관리자는 위험 판정 근거를 확인하고 오탐 또는 사고로 최종 처리할 수 있다.

### 6.5. 프로그램 생성 파일 추적 데이터

- 관리자는 프로그램 실행 파일의 게시자 서명, 경로, 생성 폴더와 보호 확장자를 등록한다.
- 에이전트는 Windows 파일 이벤트와 메일 첨부 이벤트를 시간, 경로, 크기와 SHA-256으로 연계한다.
- NTFS USN Journal, ETW 또는 FileSystemWatcher 중 실제 정확도와 권한을 기술 검증해 조합한다.
- 파일명 변경은 해시와 파일 식별 근거로 추적하고, 압축파일은 정책과 안전한 해제 한도 내에서 검사한다.
- 생성 프로세스를 확인하지 못하면 등록 프로그램 생성 파일로 단정하지 않고 신뢰도와 `확인 불가` 상태를 남긴다.
- 중앙 서버에는 기본적으로 파일 원본 대신 정책 ID, 해시, 확장자, 크기, 마스킹된 수신자와 발송 결과만 저장한다.

## 7. 위험 점수 및 대응 정책

| 등급 | 기본 점수 | 사용자 처리 | 관리자 처리 |
|---|---:|---|---|
| 안전 | 0~29 | 정상 발송·조회 | 통계만 기록 |
| 주의 | 30~59 | 경고 및 재확인 | 선택 알림 |
| 위험 | 60~79 | 발송 보류 또는 수정 요구 | 즉시 알림 및 승인 검토 |
| 긴급 | 80~100 | 정책에 따라 차단 | 긴급 알림 및 사건 대응 |

위험 점수는 헤더, 본문·URL, 첨부파일, 민감정보, 수신자 및 행동 패턴의 결과를 조합한다. 동일 사건의 중복 근거가 점수를 과도하게 높이지 않도록 상관관계를 조정하고, 규칙 및 모델 버전을 결과에 기록한다.

## 8. 4주 MVP 개발 로드맵

4주는 핵심 가설을 검증하는 MVP 기간이다. 모든 이메일 클라이언트와 조직 환경을 지원하는 상용 수준 제품 완성 기간으로 간주하지 않는다.

### 8.1. 1주차: 아키텍처 기반과 코어 분석 엔진

#### 목표

Windows 에이전트의 실행 기반과 샘플 이메일 분석 파이프라인을 완성한다.

#### 작업

- .NET 8 Windows Service와 WPF 트레이 앱 프로젝트 구성
- Named Pipe 기반 서비스·UI 통신과 장치 등록 구현
- FastAPI, PostgreSQL, Redis 개발 환경 구성
- Gmail OAuth 및 샘플 IMAP 읽기 연동
- MIME 파싱과 첨부파일 메타데이터 추출
- SPF, DKIM, DMARC 및 헤더 검증
- 민감정보 탐지·마스킹 규칙의 초기 버전
- 등록 프로그램·확장자 정책 모델과 파일 생성 이벤트 수집 기술 검증
- AI 분석 공급자 인터페이스와 JSON 응답 스키마 구현
- 테스트용 정상·피싱·정보유출 이메일 데이터셋 구성

#### 완료 기준

- 에이전트가 Windows 시작 후 자동 실행되고 트레이에 상태를 표시한다.
- `.eml` 샘플을 입력해 헤더, 본문, URL, 첨부파일과 민감정보 결과를 JSON으로 출력한다.
- 인증정보와 민감정보 원문이 로그에 남지 않는다.
- TC-FN101, TC-FN201, TC-FN205의 핵심 테스트가 통과한다.

### 8.2. 2주차: Outlook 발송 전 감시와 사용자 UI

#### 목표

지원되는 Outlook 환경에서 발송 시점을 감지하고 사용자에게 위험 경고를 제공한다.

#### 작업

- Outlook 연동 기술 검증 후 MVP 지원 버전 확정
- 수신자, 본문, URL 및 첨부파일의 발송 전 검사 연결
- 보호 대상 파일의 생성·이름 변경·첨부·발송 이벤트 연계
- 내부·외부 도메인과 유사 수신자 분석
- 허용, 경고, 보류 및 차단 정책 엔진 구현
- 트레이 상태, 분석 진행률 및 단계별 로그 UI
- 분야별 결과 카드와 “지금 바로 할 일” UI
- 오프라인 검사 큐와 서버 재연결 처리
- 에이전트 성능, 메모리 사용량 및 발송 지연 계측

#### 완료 기준

- 정상 메일, 민감정보 메일, 위험 첨부파일의 처리 결과가 정책대로 구분된다.
- 보류 메일은 승인 또는 취소 전 발송되지 않는다.
- 경고 근거에 민감정보가 마스킹되어 표시된다.
- E2E-002, E2E-003, E2E-005가 통과한다.

### 8.3. 3주차: 관리자 콘솔과 중앙 대응

#### 목표

관리자가 위험 사용자와 사건을 확인하고 대응할 수 있는 전체 흐름을 완성한다.

#### 작업

- 조직, 사용자, 장치, 정책, 사건 및 감사 데이터 모델 구현
- 위험 사용자와 미처리 사건 중심의 대시보드 구현
- 프로그램별 보호 파일 외부 전송 이력과 개인정보 유출 현황 구현
- 사건 상세, 승인, 차단, 사용자 확인 요청 및 오탐 처리
- 위험·긴급 사건의 이메일 및 Slack/Teams 알림 연동
- 정책 배포, 버전 관리 및 에이전트 동기화
- 위험 항목별 사용자 대응 매뉴얼 데이터 구성
- 전문가 상담 신청과 비식별 요약본 생성
- 역할 기반 접근통제와 조직 데이터 격리 테스트

#### 완료 기준

- 에이전트 사건이 관리자 콘솔에 나타나고 관리자 조치가 에이전트에 반영된다.
- 긴급 사건 알림에 사건 ID, 마스킹 근거 및 상세 링크가 포함된다.
- 정책 변경과 관리자 조치가 감사 이력에 기록된다.
- E2E-006, E2E-008, E2E-009가 통과한다.

### 8.4. 4주차: 통합 검증, 보안 강화 및 배포

#### 목표

제한된 사용자에게 배포 가능한 Windows MVP를 만든다.

#### 작업

- 정상·피싱·오발송·민감정보·악성 첨부 샘플 회귀 테스트
- 보호 확장자 파일의 정상 전송, 이름 변경, 압축 및 차단 회귀 테스트
- AI 정확도, 오탐률, 미탐률 및 분석 실패율 측정
- 에이전트 장시간 실행, 메모리 누수, CPU 및 발송 지연 테스트
- 외부 API 장애, 네트워크 단절, 토큰 만료 및 서버 장애 테스트
- RBAC, IPC, 로그, 로컬 저장소와 업데이트 경로 보안 검토
- MSI/MSIX 설치, 자동 시작, 업데이트 및 제거 절차 구현
- Windows 코드 서명과 서버 CI/CD 구성
- 운영자·관리자·사용자 가이드와 장애 대응 절차 작성
- 파일럿 배포 및 피드백 수집

#### 완료 기준

- 핵심 인수 테스트 E2E-001~010이 통과한다.
- 치명적·높음 등급 보안 결함이 해결되었다.
- 재부팅, 네트워크 단절 및 서버 장애 후 정상 복구한다.
- 설치, 업데이트, 롤백 및 제거 절차가 검증된다.
- 알려진 제한과 지원 대상 Outlook/Windows 버전이 문서화된다.

## 9. 상세 진단 및 대응 설계 예시

| 분야 | 문제 상태 | 사용자 행동 지침 | 기본 시스템 처리 | 참고 솔루션 |
|---|---|---|---|---|
| 정보 유출 | 주민등록번호가 외부 메일에 포함됨 | 수신자를 확인하고 민감정보를 삭제하거나 승인된 보안 전송 수단 사용 | 마스킹 경고, 정책에 따라 보류, 관리자 알림 | 조직 보안 전송 도구 |
| 수신자 | 계약서를 유사한 외부 주소로 발송 | 주소 자동완성 결과와 도메인을 다시 확인 | 재확인 팝업, 위험 시 보류 | 주소록·도메인 허용 목록 |
| 발신자 신원 | SPF/DKIM 실패 및 From 불일치 | 링크와 첨부파일을 열지 말고 피싱으로 신고 | 위험 카드 생성 및 격리 권고 | 계정 2단계 인증 |
| 본문·URL | 금융기관 사칭 피싱 점수 92 | 버튼을 누르지 말고 공식 사이트에 직접 접속 | URL 비활성화 및 긴급 경고 | 브라우저 안전 기능 |
| 첨부파일 | `.pdf.exe` 위장 실행파일 | 다운로드·실행하지 말고 이미 실행했다면 네트워크 분리 후 신고 | 발송·열기 차단 및 긴급 사건 생성 | 승인된 백신/EDR |
| 계정 | 과거 유출 이력 발견 | 비밀번호를 변경하고 재사용한 사이트도 함께 변경 | 조치 체크리스트 제공 | 암호 관리자, 2단계 인증 |

추천 제품은 특정 업체에 고정하지 않고 조직 정책, 지역, 운영체제와 최신 안전성 검토 결과에 따라 제공한다. 제휴 링크가 있으면 추천과 광고 관계를 명확히 표시한다.

## 10. 전문가 연결 시스템

### 10.1. 노출 조건

- 종합 위험 점수가 80점 이상인 긴급 사건
- 악성 첨부파일을 실행했을 가능성이 있는 사건
- 계정 탈취, 대량 유출 또는 반복 발송이 의심되는 사건
- 사용자 또는 관리자가 직접 상담을 요청한 경우

### 10.2. 처리 흐름

1. 사용자 또는 관리자가 전문가 상담을 선택한다.
2. 전달 대상 데이터, 목적과 보존 기간을 표시하고 동의를 받는다.
3. 사건 ID, 마스킹된 탐지 근거, 조치 이력과 연락 정보를 요약한다.
4. 요약본을 전송 구간에서 암호화해 지정된 상담 시스템에 전달한다.
5. Slack/Teams 등에는 개인정보가 없는 사건 알림과 보안 링크만 전달한다.
6. 전문가는 권한이 부여된 화면에서 사건을 확인하고 상담을 진행한다.
7. 상담 상태와 결과를 감사 이력에 남긴다.

Telegram이나 일반 메신저로 진단 보고서 또는 개인정보를 직접 전송하지 않는다. 메신저는 새 사건 발생 사실과 인증이 필요한 안전한 상세 링크를 알리는 용도로만 사용한다.

## 16. 실시간 IMAP 상주 감시 구현 확정

### 16.1. 연결 구조

- `imapclient`의 IMAP IDLE을 이용해 서버 변경 알림을 수신한다.
- `INBOX`와 `Sent`는 각각 독립 IMAP 연결로 선택한다. 구현은 단순 스레드 고정이 아니라 계정·폴더 연결을 관리하는 비동기 작업자로 구성한다.
- 보낸편지함 이름을 고정하지 않고 IMAP SPECIAL-USE 플래그와 공급자 매핑으로 찾는다.
- IDLE 알림은 본문 자체가 아니므로 알림 후 마지막 UID 이후 메시지만 증분 조회해 분석 큐에 넣는다.
- UIDVALIDITY, 마지막 처리 UID와 메시지 식별값을 암호화된 로컬 저장소에 기록한다.
- 공급자별 동시 연결 수와 IDLE 유지 제한을 적용하고 만료 전에 세션을 갱신한다.
- 연결 단절, 네트워크 변경, 절전 복귀와 인증 만료를 감지해 지수 백오프와 무작위 지연으로 복구한다.
- IDLE 미지원 서버는 공급자 정책을 준수하는 적응형 증분 동기화로 대체하며 과도한 단주기 폴링은 금지한다.

### 16.2. 기능 경계

`Sent` 감시는 서버에 저장된 발송 메일을 빠르게 발견하는 사후 조기 탐지다. 브라우저·모바일 등 다른 클라이언트의 발송을 IMAP만으로 사전에 차단할 수는 없다. 확실한 발송 전 검사와 차단은 Outlook 연동 또는 조직 메일 게이트웨이가 담당한다.

### 16.3. Windows 상주 방식

`.pyw`는 콘솔 창을 숨기는 프로토타입 실행 방식일 뿐 자동 복구, 권한 분리, 상태 보고와 안전한 업데이트를 보장하지 않는다. 따라서 CLI 검증이 끝난 시점(2026-09-07)부터 개발 목표를 상주형 앱으로 전환한다.

- **1단계(개인·파일럿):** 검증된 Python 감시 코드를 트레이 앱으로 감싸 단일 exe로 배포한다. 자동 시작, 단일 인스턴스, Toast 알림, 자격증명 보안 저장, 체크포인트 영속화를 포함한다. 18장 참조.
- **2단계(조직 운영):** .NET Windows Service로 자동 시작하고 WPF 트레이 앱은 사용자 알림과 제어를 담당한다. 1단계 앱은 감시 로직의 기준 구현(reference)과 회귀 테스트 오라클로 유지한다.

### 16.4. 추가 구현 및 테스트 항목

- 1주차에 INBOX·Sent 탐색, 폴더별 IDLE, UID 체크포인트와 재연결을 구현한다.
- 4주차에 다중 계정·폴더 연결 수, 장시간 메모리, 중복·누락, 절전 복귀와 인증 만료를 검증한다.
- `TC-FN104-*`, `INT-IDLE-*`, `REL-IMAP-*`, `E2E-014~015`를 완료 기준에 포함한다.
- `TC-FN105-*`, `REL-AGENT-*`, `UI-TRAY-*`로 콘솔 없는 실행, 자동 시작, 중복 실행 방지와 사용자 알림을 검증한다.
- 프로토타입에서는 `pythonw.exe realtime_email_monitor.pyw` 실행을 확인하고, 운영 빌드에서는 Windows Service 설치·복구·제거를 검증한다.

## 18. CLI 프로토타입 → Windows 상주형 앱 전환 계획

### 18.1. 배경과 결정

2026-09-07 기준 `code_snipt/realtime_email_monitor.pyw`는 Gmail 계정에 대해 다음을 실제로 검증했다.

- 앱 비밀번호 및 OAuth 2.0(XOAUTH2) IMAP 인증
- INBOX·`[Gmail]/Sent Mail` 폴더별 독립 IDLE 연결과 증분 UID 조회
- 주민등록번호·카드번호 패턴, 인증정보 키워드, 실행 가능 첨부파일 탐지와 Windows Toast 알림
- 환경 의존 결함 수정: IDLE 알림이 `idle_done` 응답에만 실리는 경우, SPECIAL-USE `\Sent` 폴더 탐색, XOAUTH2 인코딩

이 결과로 "IMAP IDLE 기반 실시간 감시가 개인 Gmail에서 동작한다"는 핵심 가설은 확인되었다. 다음 목표는 **콘솔과 환경변수 없이 Windows 로그인과 함께 메모리에 상주하며 사용자가 트레이에서 제어하는 앱**이다.

전환은 두 단계로 나눈다. Python 상주형 앱을 먼저 만드는 이유는 (1) 검증된 코드를 즉시 재사용해 1주 내 사용 가능한 앱을 확보하고, (2) 자동 시작·알림·자격증명 저장·체크포인트 등 상주형 요건을 실사용으로 먼저 검증한 뒤, (3) 그 결과를 .NET 이식의 명세와 테스트 기준으로 쓰기 위해서다.

### 18.2. 1단계: MailShield Tray (Python 상주형 앱)

#### 목표

사용자가 설치 파일 하나를 실행하면 Windows 로그인 시 자동으로 시작되고, 트레이 아이콘으로 상태를 확인하며, 위험 메일 발생 시 Toast 알림을 받는 개인용 상주 앱을 완성한다.

#### 구성

| 구성요소 | 구현 방향 | 비고 |
|---|---|---|
| 프로세스 모델 | 단일 프로세스. UI 스레드(트레이) + 폴더별 감시 스레드 + 분석 큐 | 기존 `watch_folder`·`scan_message` 재사용 |
| 트레이 UI | `pystray` 아이콘, 메뉴: 상태, 최근 사건, 일시 중지·재개, 계정 설정, 로그 열기, 종료 | 상태별 아이콘(정상·경고·연결 끊김·중지) |
| 알림 | Windows 10/11 Toast. `win10toast`는 불안정하므로 `windows-toasts` 또는 `winotify`로 교체 | 클릭 시 사건 상세 창 |
| 계정 연결 UI | Tkinter 최소 대화상자: 이메일 입력 → 공급자 자동 판별(Gmail 우선) → OAuth 브라우저 로그인 또는 앱 비밀번호 입력 | 환경변수 의존 제거 |
| 자격증명 저장 | `keyring`(Windows Credential Manager). OAuth refresh token·앱 비밀번호를 파일에 저장하지 않음 | `credentials.json`은 앱 리소스로 내장, 배포 전 프로덕션 OAuth 클라이언트 필요 |
| 체크포인트 | `%LOCALAPPDATA%\MailShield\state.json`에 폴더별 UIDVALIDITY·마지막 UID 저장. UIDVALIDITY 변경 시 재동기화 | 재시작 시 누락·중복 방지 |
| 자동 시작 | `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 등록, 설정에서 해제 가능 | 관리자 권한 불필요 |
| 단일 인스턴스 | 명명된 뮤텍스(`Global\MailShieldTray`) | 중복 실행 시 기존 인스턴스에 포커스 |
| 로깅 | 회전 로그(5MB × 5), 개인정보 마스킹 유지, 트레이 메뉴에서 열기 | 기존 `monitor.log` 형식 유지 |
| 패키징 | PyInstaller `--onefile --noconsole` → `MailShieldTray.exe`, Inno Setup 설치기 | 기존 `installer/` 스크립트 체계 확장 |
| 자원 목표 | 상주 메모리 100MB 이하, 유휴 CPU 1% 이하, IDLE 연결 폴더당 1개 | 24시간 연속 실행으로 측정 |

#### 작업 순서(1주)

| 일차 | 작업 | 산출물 |
|---|---|---|
| 1 | `code_snipt` 프로토타입을 `tray/mailshield_tray/` 패키지로 재구성: `monitor`(감시), `scanner`(탐지), `store`(체크포인트·설정), `auth`(OAuth·앱 비밀번호), `ui`(트레이·대화상자) | 패키지 골격, 기존 동작 회귀 없음 |
| 2 | 트레이 아이콘·메뉴, 상태 머신(시작·감시 중·일시 중지·재연결·오류), Toast 교체 | 콘솔 없는 실행 확인 |
| 3 | 계정 연결 대화상자, `keyring` 저장, OAuth 흐름 통합(토큰 만료 시 재로그인 안내) | 환경변수 없이 Gmail 연결 |
| 4 | 체크포인트 영속화, 단일 인스턴스, 자동 시작 등록·해제, 절전 복귀 재연결 | 재시작·절전 시나리오 통과 |
| 5 | PyInstaller 빌드, Inno Setup 설치기, 설치·제거 시 자격증명·상태 정리 | `MailShieldTray-Setup.exe` |
| 6~7 | 24시간 연속 실행, 자원 측정, 오탐 점검(주민번호·카드번호 중복 판정 분리), 사용자 매뉴얼 갱신 | 측정 보고, `04.사용자매뉴얼.md` 갱신 |

#### 완료 기준

- 설치 후 재부팅하면 로그인 30초 이내에 트레이 아이콘이 나타나고 감시가 시작된다.
- 콘솔 창, 환경변수, 수동 명령 없이 Gmail 계정을 연결하고 위험 메일 Toast를 받는다.
- 앱을 종료·재시작해도 그 사이 도착한 메일을 누락하거나 중복 알림하지 않는다.
- 자격증명이 디스크의 평문 파일에 존재하지 않는다.
- 24시간 실행 후 메모리 100MB 이하, 재연결 로그가 정상 패턴이다.
- `TC-FN104-*`, `TC-FN105-*`, `REL-IMAP-*`, `UI-TRAY-*` 중 1단계 해당 항목이 통과한다.

#### 범위 제외

- 조직 정책 동기화, 중앙 서버 보고, 관리자 콘솔 연동
- Outlook 발송 전 차단, 파일 출처 추적
- 서비스 권한 분리(1단계는 사용자 세션 프로세스)

### 18.3. 2단계: .NET Windows Service + WPF Tray 이식

#### 목표

1단계에서 실사용으로 확정된 감시·탐지 동작을 `agent/MailShield.Agent`에 이식하고, 조직 배포 요건을 충족하는 서비스·트레이 구조로 완성한다.

#### 이식 항목과 현재 격차

| 항목 | 1단계(Python) 검증 결과 | `MailShield.Agent` 현재 상태 | 이식 작업 |
|---|---|---|---|
| IDLE 처리 | 알림 후 마지막 UID 이후만 조회, `N:*` 경계 처리 | `SearchQuery.All`로 전체 검색, `lastUid` 메모리 변수 | UID 범위 검색, 체크포인트 영속화(DPAPI) |
| 보낸편지함 탐색 | SPECIAL-USE `\Sent` → 이름 후보 순서 | `Sent` 문자열 고정 | MailKit `SpecialFolder.Sent` 우선, 후보 대체 |
| 인증 | 앱 비밀번호 + OAuth XOAUTH2 | 환경변수 앱 비밀번호만 | Credential Manager 읽기, `SaslMechanismOAuth2` 추가 |
| 탐지 규칙 | 정규식 3종 + 첨부 확장자 | `DlpScanner` 정책 기반 | 1단계 오탐 데이터로 규칙 보정, 카드번호 체크섬 |
| 사용자 UI | Python 트레이 | 없음 | WPF 트레이 프로젝트 신설, Named Pipe로 서비스와 통신 |
| 설치 | Inno Setup(1단계 확장) | Inno Setup 서비스 설치 스크립트 존재 | 서비스+트레이 동시 설치, 서명, 롤백 |

#### 완료 기준

- 1단계 앱과 동일한 테스트 메일 세트에 대해 동일한 사건을 생성한다(회귀 오라클).
- 서비스는 LocalService 권한, 트레이는 사용자 권한으로 분리 실행된다.
- `installer/Verify-MailShieldService.ps1`가 서비스 설치·자동 시작·복구를 통과한다.
- 3장 상용 계획서 Phase 1 완료 기준을 충족한다.
